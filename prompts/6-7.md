# ORust Phase 6 + 7: Comments, documentation, metadata, then release hardening

Read AGENTS.md first. All hard rules still apply: rustc is the source of truth, no inheritance, no hidden Rc/RefCell, errors shown in .or terms, nothing hidden by default, unsupported features fail with a clear "not supported yet" message instead of being faked. Continue milestone numbering from Phase 5 (which ended at 38; the tooling track T1-T6 may be in progress and this phase must integrate with it). Do not start Phase 7 until Phase 6 tests are green.

## Goals
- Phase 6 gives ORust first-class comments and documentation: every comment is preserved by the toolchain, doc comments become real rustdoc, doc tags such as `@author`, `@param`, `@throws`, `@since`, `@deprecated` are understood and checked, examples inside docs are compiled and run as tests, and `orust doc` produces a documentation site in ORust syntax.
- Phase 7 closes the project: a written spec, a conformance suite, stability and versioning rules, performance, packaging and publishing, an exit ramp to plain Rust (`orust eject`), a book and tour, security and governance, and an automated 1.0 release gate.

## Cross-cutting rules for this whole prompt
1. **Comments are data, not noise.** The lexer keeps all comments as trivia attached to tokens. Nothing downstream may discard them. The formatter, doc generator, LSP, and `emit` all depend on this.
2. **Two different `@` things; keep them separate.** (a) Doc tags live only inside doc comments (`/// @author ...`). (b) Annotations live in code (`@data class Foo`). The lexer decides by context, and a doc tag outside a doc comment is an ordinary comment. Document the distinction in docs/annotations-vs-doc-tags.md.
3. **Docs never change behavior.** Removing every comment from a program must not change its emitted Rust except for comments and attributes that map to documentation (`#[deprecated]` is the one deliberate exception, because it is a user-facing API signal; log it in docs/decisions.md).
4. **Spans stay exact.** Doc and comment text is not tracked by the borrow-error span table, but adding or removing comments must never shift which `.or` line an error points at. Add a regression test that inserts 100 comment lines at the top of every golden test and asserts the translated errors point at the shifted, still-correct lines.
5. **Verify toolchain behavior empirically.** Wherever this prompt describes how rustdoc, cargo, or crates.io behaves, write a small test that checks it on the CI toolchain and log the result in docs/decisions.md. If reality differs from this prompt, follow reality.
6. **OR codes.** Every new lint and error gets an `ORxxxx` code in docs/error-codes.md with an explanation reachable via `orust explain`.

# PHASE 6: COMMENTS AND DOCUMENTATION

## Milestone 39: Trivia-preserving lexer and parser
Comment forms:
| Form | Kind | Notes |
|---|---|---|
| `// text` | line comment | |
| `/* text */` | block comment | **nests**: `/* a /* b */ c */` is one comment (same as Rust and Dart); unterminated block comment is an error pointing at the opener |
| `/// text` | outer doc comment | documents the next item; exactly three slashes (`////` is a plain comment) |
| `/** text */` | outer block doc | `/**/` and `/***/` are plain comments |
| `//! text` | inner doc comment | documents the enclosing file/module/class; must appear at the start of the file or the start of a class body |
| `/*! text */` | inner block doc | same |
| `#!shebang` | shebang | first line only, preserved, ignored by the parser |

Requirements:
- Handle a leading UTF-8 BOM, CRLF and LF (preserve the file's existing line endings on formatting), tabs, and non-ASCII text in comments.
- **Attachment rules** (write them down in docs/comments.md and test each): a comment is *leading* trivia of the next token, or *trailing* trivia if it is on the same line after a token. A comment on its own line followed by a blank line is *detached* (it documents nothing). Inner docs attach to the container. Comments inside an expression, parameter list, or argument list stay with their nearest token.
- A doc comment that has nothing to document (before `}` or end of file, or detached by a blank line) is a lint, not an error: `OR0601 doc comment documents nothing`.
- AST nodes expose `leading_trivia()`, `trailing_trivia()`, and `docs()`. Add a lossless-roundtrip test: for every golden `.or` file, `print(parse(src))` with trivia reproduces the source byte-for-byte (the "CST roundtrip" property). Run it under proptest on random insertions of whitespace and comments.
- Update the formatter (T1) to preserve comments, keep blank-line structure, and never move a comment across a statement. Update its idempotence tests.
- `orust emit --comments` (default on for `emit`, off for `build`) carries plain comments into the generated Rust next to the code they belonged to, so the output stays readable and `orust eject` (milestone 53) has something to work with.

## Milestone 40: Doc comment model and tag grammar
Doc comments are Markdown (CommonMark) with an optional tag section. Parse into:
````rust
struct DocBlock {
    summary: String,            // first paragraph
    body: Markdown,             // everything before the first tag
    tags: Vec<DocTag>,          // in source order
    span: Span,
}
enum DocTag { Author{name,email,url}, Param{name,desc}, TypeParam{name,desc}, Returns(desc),
    Throws{ty,desc}, Panics(desc), Example{title,code}, See(link), Since(version), Deprecated{since,note},
    Version(String), Todo(String), Note(String), Warning(String), Internal, Category(String),
    InheritDoc, License(String), Copyright(String), Unknown{name, text} }
````
Tag syntax: a tag starts at the beginning of a doc line (after optional `*` in block docs) with `@name`, and continues over following lines until the next tag or the end of the block. Inline tags use braces: `{@link Name}`, `{@code expr}`. Markdown intra links `[Name]`, `[Name.method]`, `[pkg:other.Name]` are also links (resolved in milestone 41). Text inside backtick code spans and fenced code blocks is never scanned for tags, so an email address or an annotation inside code is safe.

Tag reference (implement all; each row also defines where the tag is allowed):
| Tag | Meaning | Allowed on | Rustdoc rendering |
|---|---|---|---|
| `@author Name <email> (url)` | who wrote it; repeatable | file, class, function | `# Authors` list |
| `@param name desc` | parameter; repeatable | function, method, constructor | `# Arguments` list |
| `@typeParam T desc` | generic parameter | generic items | `# Type parameters` |
| `@returns desc` | return value | function with a return value | `# Returns` |
| `@throws Type desc` | error type and when | function with `throws` | `# Errors` |
| `@panics desc` | when it panics | function | `# Panics` |
| `@example [title]` + fenced code | runnable example (compiled by `orust test --doc`) | any item | `# Examples` |
| `@see Link` | related item | any | `# See also` |
| `@since 1.2.0` | version introduced | any exported item | italic "Since" line |
| `@version 1.2.0` | document version | file, class | rendered line |
| `@deprecated [since X] note` | deprecation | any | `#[deprecated(since, note)]` plus section |
| `@todo text` | tracked work | any | hidden from rustdoc; collected by `orust todo` |
| `@note`, `@warning` | callouts | any | blockquote with a label |
| `@internal` | not public API | any | `#[doc(hidden)]` |
| `@category name` | grouping in the generated site | exported items | site only |
| `@inheritDoc` | copy docs from the interface method this implements | method | text copied at build time |
| `@license SPDX-id`, `@copyright text` | legal | file | file-header docs |

Behavior:
- **Inheritance of defaults:** a file with a header `@author` applies that author to every item in the file that has no `@author` of its own for the *generated site only* (do not emit the inherited copy into each rustdoc block). The package-level `authors` in orust.toml are the final default.
- `@inheritDoc` pulls the summary, `@param`, `@returns`, and `@throws` text from the interface method; if there is none, `OR0602`.
- Tag order in source does not matter; output order is canonical (summary, body, Type parameters, Arguments, Returns, Errors, Panics, Examples, See also, Authors, Since).
- Unknown tag: `OR0603 unknown tag @authro, did you mean @author?` (edit distance suggestion). Unknown tags are preserved in output as plain text so nothing is lost.
- Markdown is passed through as written; do not reflow user text in `emit` (the formatter may reflow only with `--reflow-docs`, off by default).

## Milestone 41: Documentation emission to rustdoc
Doc comments become `///` and `//!` comments on the emitted Rust items, so plain Rust users running `cargo doc` get real documentation for any exported ORust item. Rules:
- Summary and body are copied; tags are converted per the table into the standard rustdoc section headings (`# Arguments`, `# Errors`, `# Panics`, `# Examples`). Use the headings Rust's API guidelines already use for Errors, Panics, Safety, and Examples; log the non-standard ones.
- `@deprecated` emits `#[deprecated(since = "...", note = "...")]` on the emitted item. `@internal` emits `#[doc(hidden)]`.
- **Doc links.** Resolve `[Name]`, `[Name.method]`, `{@link Name}` against the ORust symbol table (honoring imports from Phase 3) and rewrite to the emitted Rust path using the naming bridge (`Invoice.applyDiscount` becomes ``[`Invoice::apply_discount`]``). Unresolvable links are `OR0604 broken doc link` (error in `--deny-warnings`, warning otherwise).
- **Code fences.** ```` ```orust ```` blocks are kept in the output with the `orust` info string. **Verify empirically** that rustdoc does not try to compile them as Rust doctests (blocks tagged with an unknown language should be skipped; if this fails on the CI toolchain, rewrite the info string to `text` and note the original in an HTML comment). Fences tagged `rust` are passed through unchanged and ARE compiled by rustdoc as normal. Support `ignore`, `no_run`, `should_fail` (mapped to `should_panic` semantics, see milestone 42), and `compile_fail` on `orust` fences.
- **Hidden lines:** inside an `orust` example, a line starting with `# ` is compiled but not shown (same convention as rustdoc), so examples can include setup without clutter. Test that the rendered output omits them.
- Emit module docs from file-level `//!` onto the generated module. Class docs go on the struct; constructor docs go on `new`; field docs on fields; interface docs on the trait; `error` case docs on enum variants; enum variants and `test`/`group` blocks keep their docs too.
- Add `orust doc --rustdoc` which runs `cargo doc` on the generated crate for Rust-side consumers and prints the output path.

Acceptance program (must work, and must produce rustdoc without warnings):
````orust
//! Billing utilities.
//!
//! @author Ada Lovelace <ada@example.com>
//! @since 0.2.0

/// A customer invoice.
///
/// Totals are kept in cents to avoid floating point rounding errors.
///
/// @author Ada Lovelace
/// @since 0.2.0
/// @example Discounting an invoice
/// ```orust
/// var inv = new Invoice(1000);
/// inv.applyDiscount(10);
/// expect(inv.total == 900);
/// ```
export class Invoice {
  /// Total in cents. Never negative.
  int total;

  Invoice(this.total);

  /// Applies a percentage discount to the total.
  ///
  /// @param percent Whole number from 0 to 100.
  /// @throws DiscountError if `percent` is outside 0 to 100.
  /// @see [Invoice.total]
  void applyDiscount(int percent) throws DiscountError {
    if (percent < 0 || percent > 100) { throw DiscountError.OutOfRange(percent); }
    total = total * (100 - percent) / 100;
  }

  /// @deprecated since 0.3.0 Use [applyDiscount] instead.
  void discount(int p) { applyDiscount(p); }
}

/// Why a discount was rejected.
export error DiscountError {
  /// The percentage was not between 0 and 100.
  OutOfRange(int percent) => "discount out of range: $percent",
}
````
Expected emitted Rust shape (formatting and section text may be refined):
````rust

    /// [`DiscountError`]: if `percent` is outside 0 to 100.
    ///
    /// # See also
    /// [`Invoice::total`]
    pub fn apply_discount(&mut self, percent: i64) -> Result<(), DiscountError> { /* ... */ }

    /// Use [`Invoice::apply_discount`] instead.

````
`cargo doc` on the output must finish with zero warnings (broken intra-doc links and invalid HTML are rustdoc warnings; fix the generator, not the test).

## Milestone 42: Doctests (`orust test --doc`)
- Collect every `orust` fenced example (including `@example`) from doc comments. For each, generate a test that compiles and runs it through the normal ORust pipeline: wrap the snippet in a `main` unless it already defines one (same wrapping convention as rustdoc), prepend `import` lines for the documented item's own file so the snippet can use it, honor hidden `# ` lines, and run under the same cargo test harness so results appear in `orust test` output as `doc: Invoice (billing.or:12)`.
- Fence flags: `ignore` (skipped, reported as ignored), `no_run` (compile only), `should_fail` (must throw or panic, mirrors `should_panic`), `compile_fail` (must fail to compile; optionally `compile_fail(E0382)` or `compile_fail(OR0123)` pins the code), `edition2026`.
- Errors inside a doctest are translated like any other and point at the `.or` file and the correct line **inside the doc comment**, not at a generated file. Add a golden test for this mapping.
- `orust test --doc` runs only doctests; plain `orust test` runs unit tests plus doctests (`--no-doc` disables). Doctests run in parallel in isolated temp crates sharing one target dir for speed; set a per-test timeout.
- Examples that use `std:http` or other network features must be `no_run` or `ignore` (lint `OR0605` if a doctest tries network access without `no_run`).

## Milestone 43: Documentation lints, TODO tracking, suppressions
Lints (all configurable in orust.toml `[lints]` as `allow|warn|deny`; the default level is in parentheses):
| Code | Lint | Default |
|---|---|---|
| OR0601 | doc comment documents nothing | warn |
| OR0602 | `@inheritDoc` with no parent doc | warn |
| OR0603 | unknown doc tag (with suggestion) | warn |
| OR0604 | broken doc link | warn |
| OR0605 | doctest uses network without `no_run` | warn |
| OR0606 | `missing_docs` on an exported item | allow (deny in `orust new --lib` templates) |
| OR0607 | `@param` names a parameter that does not exist, or a real parameter is undocumented in a documented function | warn |
| OR0608 | `@throws` type does not match the function's `throws` type, or `throws` function has no `@throws` | warn |
| OR0609 | `@returns` on a function that returns nothing | warn |
| OR0610 | `@since` is greater than the package version, or earlier than the package's first release | warn |
| OR0611 | `@deprecated` item still used inside this package | warn (translate rustc's `deprecated` lint to: "`discount` is deprecated since 0.3.0: Use applyDiscount instead.") |
| OR0612 | duplicate tags where only one is allowed (`@since`, `@version`, `@returns`) | warn |
| OR0613 | docs empty after tag removal (summary missing) | warn |
| OR0614 | summary line longer than 120 characters or not ending as a sentence | allow |
| OR0615 | `TODO`/`FIXME`/`HACK`/`XXX` comment present | allow (deny in CI profile) |
- **Suppression comments:** `// orust:allow(OR0607)` on the line before an item (or at file top for the whole file), `// orust:allow-next-line(OR0615)`, and `// orust:fmt off` / `// orust:fmt on` to protect a region from the formatter. Unknown codes in a suppression are `OR0616`.
- `@todo` tags and `TODO(name): text` comments are collected by `orust todo [--format table|json|markdown] [--author name]`, listing file, line, text, and optional owner. `--deny` exits nonzero if any exist (for CI).
- Every lint has a minimal failing example in docs and an `orust explain ORxxxx` entry whose example is verified by a test, as in the earlier tooling track.

## Milestone 44: `orust doc` site generator
Generate a static documentation site directly from the ORust AST (not from rustdoc), so signatures are shown in ORust syntax (`void applyDiscount(int percent) throws DiscountError`, not the Rust form).
- Output: `target/orust/doc/` with an index page per package, a page per file/module, per class/interface/enum/error/function, a sidebar, and a client-side search powered by a JSON index (no external service, no CDN, no JS framework; plain HTML/CSS/JS, works from `file://`).
- Each item page shows: signature, summary, body, parameters table, returns, throws (linked to the error type), examples (syntax-highlighted; examples that have a doctest show a pass/fail badge from the last `orust test --doc` run when available), `@see` links, `@author` list, `@since`/`@version` badges, deprecated banner, `@category` grouping, and a **"Rust" toggle** that shows the emitted Rust signature and a link to the `.or` source line. Inherited docs and implemented interfaces are listed. `@internal` items are hidden unless `--document-internal`.
- Cross-package links to dependencies that have docs; links to `docs.rs` for Rust crates.
- Features: `--open`, `--serve [port]` (tiny local file server, hot reload on file change using the T4/LSP file watcher), `--format html|markdown|json` (the JSON model is the stable contract for tools and is documented in docs/doc-json.md), `--theme light|dark|auto`, `--private` (include non-exported items), and a **`--check` mode** that fails when any public item lacks docs or any link is broken, for CI.
- Accessibility baseline: semantic HTML, keyboard navigation, `prefers-color-scheme`, contrast-checked colors, no content that requires JS to read.
- Snapshot-test the generated HTML for the acceptance program (stable ids and ordering so snapshots are not flaky).

## Milestone 46: Annotation catalog (finalize)
Annotations (`@name` or `@name(args)`) precede declarations and members. Finalize this catalog, each with grammar, emitted Rust, errors, and one test:
| Annotation | Effect |
|---|---|
| `@data` | derive Debug, Clone, PartialEq, Eq, Hash where allowed (from Phase 2) |
| `@json`, `@json(name: "x")` | serde derive (from Phase 4) |
| `@override` | the method must implement an interface method, otherwise `OR0620 nothing to override` |
| `@deprecated`, `@deprecated("note", since: "0.3.0")` | `#[deprecated]` (same as the doc tag; if both exist, the annotation wins and the doc tag is merged into the note) |
| `@mustUse`, `@mustUse("reason")` | `#[must_use]` |
| `@inline`, `@inline(always|never)` | `#[inline]` variants |
| `@rustName("exact_name")` | override naming bridge (from Phase 3) |
| `@derive(Name, ...)` | extra derives, only from an allowlist (`Copy`, `PartialOrd`, `Ord`, `Default`, `Serialize`, `Deserialize`) |
| `@rust(attr...)` | raw passthrough: `@rust(cfg(test))` emits `#[cfg(test)]`. Requires a `rust` import-level opt-in in orust.toml (`[features] raw_attributes = true`), and is flagged by `orust audit` (milestone 55) |
| `@unstable("feature-name")` | marks a feature as unstable; usable only if enabled in orust.toml `[unstable]` (milestone 50) |
Rules: annotations may be written on one line or stacked; order is irrelevant; duplicates are `OR0621`; an unknown annotation is `OR0622 unknown annotation @jsn, did you mean @json?`; annotations on the wrong target (`@override` on a class) say which targets are valid. Update the formatter, LSP completion, and `orust explain`.

# PHASE 7: CLOSING AND RELEASE HARDENING

## Milestone 48: Lexical and grammar specification
Write `spec/` (mdBook): lexical structure and grammar, as the authoritative reference.
- **Lexical:** identifiers (Unicode XID with NFC normalization; reject confusable-script mixing with a warning), the complete keyword table split into reserved, contextual (`show`, `hide`, `as`, `export`, `private`, `internal`, `on`, `test`, `group`, `when`, `error`, `from`, `lend`, `copy`, `drop`, `spawn`, `await`, `async`, `throws`, ...), and **reserved for the future** (so adding them later is not a breaking change; pick a conservative list and log it), literals (integers with `_`, hex/octal/binary, suffixes, floats with exponents, characters, strings), **string forms**: single and double quotes, escapes (`\n \t \r \\ \" \' \$ \u{1F600} \xNN`), `$name` and `${expr}` interpolation, raw strings `r"..."`, and multi-line strings `"""..."""` with documented indentation-stripping rules and interpolation inside them. Line terminators, whitespace, and comment grammar from milestone 39.
- **Grammar:** EBNF for every construct implemented through Phase 6, generated from or checked against the parser (a test parses every EBNF production's examples; a "grammar drift" test fails if the parser accepts something the spec does not describe or the reverse).
- Each spec section has an ID (`lex.string.raw`, `decl.class.constructor`, `ownership.lend.mut`, ...). Tests reference these IDs (milestone 49).
- Add any lexical gaps discovered (raw strings, multi-line strings, numeric suffixes) as implementation work in this milestone, with golden tests.

## Milestone 49: Conformance suite and spec coverage
- Convert the golden suite into a conformance suite: each test declares `// spec: <section-id>` and an expected outcome (`runs` with stdout, `emits` Rust, `errors` with an OR code, or `parse-error`). `cargo xtask conformance` runs them and prints a per-section matrix.
- `cargo xtask spec-coverage` fails if any spec section has zero tests or any test references an unknown section ID.
- The suite must be implementation-neutral (no references to Rust internals beyond observable output) so another implementation could use it. Document how to run it.

## Milestone 50: Stability, versioning, editions
- Semantic versioning for the toolchain; separate versioning for the language via editions (`edition = "2026"`, from T5). Write docs/stability.md covering: what is guaranteed stable (accepted syntax, emitted public API shape and naming bridge, OR codes and their meanings, `orust.toml` keys, the doc JSON model, the CLI flags), what is not (exact emitted Rust formatting, wording of messages, internal crates), and the deprecation policy (a feature is deprecated for at least one minor release with a warning and a migration note before removal, and removals happen only at an edition boundary).
- **Unstable features:** `@unstable("name")` and an `[unstable]` table in orust.toml gate experimental syntax; using one without the opt-in is `OR0630`. Stable code never depends on them.
- **Compatibility tests:** a directory of old-edition programs and their expected outputs from each past release (`tests/compat/<version>/`), run in CI, so regressions are caught. `orust fix --edition` applies mechanical migrations where possible.
- Pin and test the MSRV; document the Rust versions supported for the *generated* code (the generated crate's `rust-version` is set explicitly in Cargo.toml).
- `orust --version --verbose` prints toolchain versions, edition support, enabled features, and the rustc it found.

## Milestone 51: Performance and incremental builds
- Per-file cache keyed by content hash plus compiler version plus relevant config; unchanged files are neither re-parsed nor re-emitted. **Never rewrite a generated file whose bytes did not change** (otherwise cargo rebuilds everything because of mtimes); test this by comparing mtimes across two builds.
- Parse and lower files in parallel (rayon is allowed for this milestone only; log it). Resolve imports first to order work and detect cycles without deadlocks.
- Benchmarks (`cargo xtask bench`, using criterion or a simple harness): lex+parse+emit throughput on a generated 100k-line project, memory ceiling, cold vs warm `orust check`. Record a baseline file in the repo and fail CI on a regression greater than 15 percent.
- Reproducible output: identical inputs give byte-identical generated Rust (sorted maps, no timestamps in generated files except the version notice; if the notice includes anything that varies, remove it). Test by building twice in different directories and diffing.
- `orust clean` removes generated trees and caches; `orust check` should never invoke codegen for crates that cargo already considers fresh.

## Milestone 52: Packaging and publishing
- `orust package` produces a publishable crate: the generated Rust, the original `.or` sources (under `orust-src/`), `orust.toml`, README, LICENSE files, and generated Cargo.toml with `include` rules; the crate compiles with plain `cargo` and **without the orust compiler installed** (consumers only need Rust). Verify by building the packaged crate in a clean directory with no orust on the PATH.
- `orust publish` runs `orust package`, runs all lints and tests, validates metadata (milestone 45), then delegates to `cargo publish` (never reimplement a registry client; support `--dry-run`, `--registry`). It refuses to publish with `@unstable` features, with `path` dependencies, or with failing doctests, and prints a pre-flight checklist.
- Dependencies between ORust packages are published and consumed as crates; `import 'package:x/...'` resolves via the dependency's included `orust-src/` so signatures and docs are available to the ORust front end (milestone 19 groundwork). Pin and document the lockfile behavior.
- Distribution: `cargo install orust`, `cargo binstall` metadata, release binaries for Linux/macOS/Windows (x86_64 and aarch64) with checksums and signatures, a Homebrew formula and Scoop manifest template in `packaging/`, and a small `install.sh`/`install.ps1` that verifies checksums. No auto-update and no telemetry.

## Milestone 53: `orust eject` (the exit ramp)
Users must never feel locked in. `orust eject [--out dir] [--keep-runtime]` converts an ORust project to a plain Rust project:
- Writes the generated Rust as the new source of truth: formatted with rustfmt, **comments and doc comments preserved**, original `///` docs converted to the standard section headings, `.or` doc tags that have no Rust equivalent preserved as plain Markdown, and the generated-file notice removed.
- Produces a clean Cargo.toml; by default vendors the small `orust-runtime` pieces actually used (Error, Task, duration helpers) into a `support.rs` module (or depends on the crate with `--keep-runtime`), so the result has no dependency on the ORust toolchain.
- Names follow the naming bridge, which is already idiomatic Rust; ownership constructs (`lend`, `copy`, `shared`) are already ordinary Rust in the output.
- The ejected project must compile with `cargo build` and pass `cargo test` with the same results as the ORust project (doctests converted: `orust` fences become `text` fences plus equivalent unit tests; report in `EJECT_NOTES.md` anything that could not be converted automatically).
- Test: eject every acceptance project from every phase in this series, build and test them with plain cargo, and compare stdout to the ORust run. This test must pass for the project to be considered releasable.

## Milestone 54: The book, the tour, the playground
- **The ORust Book** (mdBook, `book/`): a guided path from zero to a real program, with chapters aligned to the learning ladder (Level 1-4 from AGENTS.md), plus reference chapters (spec links), a "Reading errors" chapter built from `orust explain` content, and an "Ownership for people who know Dart/Java/C#/Swift/Python/C++" chapter. **Every code block in the book is compiled or checked** (`orust test --book`), with the same `ignore`/`no_run`/`compile_fail` flags as doctests; CI fails on a broken example.
- **Cheat sheets** in `docs/for-*.md`: ORust for Dart, Java, C#, Swift, and Python developers (side-by-side tables), and "Graduating to Rust" (ORust construct to Rust construct, with `orust eject` instructions).
- **`orust tour`:** an interactive terminal tutorial with ~25 short exercises (each has a prompt, a starting file, hints, and a check); progress stored locally; the exercises are plain `.or` files plus a `tour.toml`, so contributors can add more.
- **Playground (stretch):** a WASM build of the parser, lowerer, and emitter (no rustc in the browser) that shows the emitted Rust live, the doc preview, and friendly parse errors, plus a "Run on the Rust Playground" link that opens the emitted code on play.rust-lang.org (verify the URL format at implementation time; do not hard-code it without a test). The translator for rustc errors is not available in the browser; say so on the page.

## Milestone 55: Security, supply chain, governance
- **`orust audit`:** lists `rust { }` blocks, `@rust(...)` attributes, build scripts, `unsafe` appearing in raw blocks, `import 'rust:...'` of crates, and network-capable std modules in use; summarises per file. Pairs with the existing lints: `OR0640 raw Rust block in file X`.
- **Compiler hygiene:** no network access during compile except cargo fetching dependencies the user listed; the compiler never executes code from the project other than through cargo; document the threat model in SECURITY.md (untrusted `.or` source can contain `rust {}` and build scripts, so building untrusted projects is as dangerous as building untrusted Rust).
- CI: `cargo deny` (licenses, bans, advisories) and `cargo audit` as required checks, `cargo vet` or an equivalent review policy is optional, dependency updates by a scheduled bot-friendly config (`dependabot.yml` or `renovate.json`), SBOM generation on release (CycloneDX), release builds from a clean CI job (not developer machines), checksums and signatures published with every release.
- **Governance docs:** LICENSE (MIT and Apache-2.0), `CONTRIBUTING.md` (including "adding a lint", "adding a doc tag", "adding an annotation", "adding a spec section"), `CODE_OF_CONDUCT.md`, `SECURITY.md` (private reporting address and response targets), issue and PR templates, `CHANGELOG.md` in Keep a Changelog format, `ROADMAP.md`, and an RFC process (`rfcs/0000-template.md`, a README explaining when an RFC is required: any change to syntax, emitted public API, or stability promises).
