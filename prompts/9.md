# ORust Phase 9: Unified CLI (orust as a front door to cargo, with ORust's own commands)

Read AGENTS.md first. All hard rules still apply: rustc and cargo are the source of truth, errors are shown in .or terms, nothing is hidden by default, unsupported things fail with a clear "not supported yet" message instead of being faked. Continue milestone numbering from Phase 8 (which ended at 62). This phase also finalizes the CLI surface mentioned in earlier phases (`orust check|build|run|emit`, `orust test`, `orust doc`, `orust fmt`, `orust new`, `orust add`, `orust publish`, `orust explain`, `orust eject`, ...); where an earlier milestone defined a command differently, this phase's classification table wins and the earlier docs must be updated.

## Goal
One binary, `orust`, that is a superset of cargo's command line:
1. Every cargo command and every cargo alias is reachable as `orust <name>`. In an ORust project it runs against the generated Rust project (regenerating first when `.or` files changed) and translates diagnostics back to `.or`. In a plain Rust project, or for commands that need no project, it behaves exactly like cargo.
2. ORust's own commands live beside them (`emit`, `explain`, `eject`, `tour`, `todo`, `authors`, `audit`, `doctor`, ...).
3. `orust --help` and `orust --list` show everything in one merged view, and every entry is labeled with where it comes from: ORust, cargo, cargo enhanced by ORust, alias, or third-party cargo extension.
4. A user can always get the real, untouched cargo behavior (`orust cargo ...`, `--raw`) and can always see exactly what cargo command ORust ran (`--show-cargo`).

## Hard rules for this phase
1. **Never reimplement cargo.** Dependency resolution, building, publishing, registries, and locking stay cargo's job. We wrap, we do not replace. The one exception is editing `orust.toml`, which cargo cannot do.
2. **Never use a shell.** Spawn cargo with `std::process::Command` and an argument vector. No string concatenation, no `sh -c`, no `cmd /c`.
3. **Unknown means pass through.** An unknown flag, an unknown command, or a flag ORust has no opinion about reaches cargo byte-for-byte, in the original order, including empty strings, spaces, `=`, and non-ASCII. Test this with proptest.
4. **Exit codes and streams are preserved.** The exit code is cargo's (or the program's, for `run`). A signal-terminated child maps to the conventional 128+N on Unix. Program output from `run` and test binaries is never captured, reordered, or colored by us. Nothing ORust prints may contaminate a machine-readable mode (`--message-format=json*`, `--format json`, `metadata`, `--list --format json`).
5. **Every ORust-only flag is documented and collision-free.** A flag ORust adds must not exist in cargo for the same command. A flag cargo already owns keeps cargo's meaning, with the exceptions in the collision registry below (ORust's meaning wins, and the cargo meaning stays reachable via `orust cargo ...`). A test must enforce this by parsing real `cargo <cmd> --help` output.
6. **The label is the truth.** Every command shown in help carries its origin tag, and the tag must match the actual routing. A test cross-checks help output against the routing table.
7. **Offline and private.** No telemetry, no network access of our own, no auto-update. Anything networked is cargo's.
8. **Discover, don't hard-code, where cargo can tell us.** The list of cargo commands, aliases, and installed extensions comes from the cargo that will actually run (`cargo --list` and config files), with a built-in fallback table only for descriptions and classification defaults. Cargo versions differ; our tool must degrade gracefully when a command is missing or new.

## Command classes (the routing table)
Every command name resolves to exactly one class. This table is the default; users cannot change a class except for extensions (see config).

| Class | Tag shown in help | Meaning |
|---|---|---|
| Native | `[orust]` | exists only in ORust |
| Replaced | `[orust]` plus note "replaces cargo X" | ORust implementation of a name cargo also has, because cargo's version would be wrong or useless on generated code |
| Enhanced | `[cargo+]` | the cargo command, run against the generated project, with `.or` diagnostics, `.or` awareness, and the same flags |
| Passthrough | `[cargo]` | the cargo command, exactly as cargo behaves |
| Alias | `[alias]` | an alias from `orust.toml` or cargo config, with its expansion and source file shown |
| Extension | `[cargo-ext]` | a third-party `cargo-*` binary found on PATH |

Default assignments (write as data in `crates/orust-cli/src/registry.rs` plus a generated `docs/cli-commands.md`):

| Command | Class | Behavior |
|---|---|---|
| `emit` | Native | print generated Rust for a file or project |
| `explain` | Native | lesson for an OR code or a rustc code |
| `eject` | Native | convert to a plain Rust project |
| `tour` | Native | interactive tutorial |
| `todo`, `authors`, `audit` | Native | collected TODOs, authors, raw-Rust and unsafe audit |
| `doctor` | Native | environment and project health check (milestone 69) |
| `completions`, `man` | Native | shell completions, man pages |
| `alias` | Native | `orust alias list` shows every resolved alias and where it came from |
| `cargo` | Native | `orust cargo <args...>` runs real cargo with zero translation in the current directory (see "raw escape") |
| `new`, `init` | Replaced | create ORust projects (`--lib`, `--bin`, `--name`, `--vcs`, `--edition` accepted with cargo's meanings; cargo-only flags give a clear error) |
| `add`, `remove` | Replaced | edit `orust.toml` dependencies (see milestone 66) |
| `fmt` | Replaced | format `.or` files; `orust fmt --rust` additionally runs rustfmt on plain `.rs` files that live in the source tree |
| `fix` | Replaced | ORust edition and syntax migrations; `cargo fix` would edit generated files that get overwritten, so it is not offered as `[cargo+]` (reachable only through `orust cargo fix`, with a warning) |
| `doc` | Replaced | the ORust documentation site (milestone 44); `orust doc --rustdoc [cargo doc args]` runs `cargo doc` on the generated crate |
| `package`, `publish` | Replaced | milestone 52 flows that validate, then delegate to cargo |
| `build`, `check`, `run`, `test`, `bench`, `clippy`, `rustc`, `rustdoc` | Enhanced (translated) | regenerate, run cargo on the generated project, map diagnostics to `.or` |
| `clean` | Enhanced | cargo clean plus generated-tree cleanup (`--keep-generated` skips that part) |
| `tree`, `metadata`, `fetch`, `update`, `vendor`, `generate-lockfile`, `locate-project`, `pkgid`, `verify-project`, `read-manifest`, `report`, `install --path` | Enhanced (project-bound, no diagnostics translation) | regenerate if stale, run on the generated project |
| `install` (no `--path`/`--git`-to-ORust), `search`, `login`, `logout`, `owner`, `yank`, `version`, `help` (cargo topics), `config`, `uninstall` | Passthrough | cargo verbatim |
| any other `cargo-*` on PATH | Extension | policy below |

Extension policy: default `run_in = "generated"` for extensions when inside an ORust project (so tools like `cargo nextest`, `cargo expand`, `cargo deny`, `cargo audit` see the real Rust crate), `"root"` otherwise. Set the `CARGO_MANIFEST_DIR`-style context only through cwd, never through invented environment variables. Users override per extension in `orust.toml`:
```
[cli.extensions]
nextest = { run_in = "generated", translate = true }   # translate compiler diagnostics if it emits cargo-style JSON (opt-in)
deny    = { run_in = "root" }                          # operates on Cargo.lock or config at the project root
```
`orust doctor` warns on extensions that are likely mis-routed (tools known to need the root, found with `run_in = "generated"`) using a small built-in hint list kept in data, not code.

## Flag collision registry (data file `collisions.toml`, tested)
| Command | Flag | Resolution |
|---|---|---|
| `test` | `--doc` | ORust meaning wins: run only ORust doctests (milestone 42). Rust doctests of generated code: `orust cargo test --doc`. Help shows `--doc (orust meaning)` |
| `test` | `--no-doc` | ORust-only: skip ORust doctests |
| `run`, `check`, `build` | first positional ending in `.or` | single-file mode (earlier CLI definition) |
| any | `--manifest-path <p>` | accepts `orust.toml` (ORust project) or `Cargo.toml` (plain Rust); when it points at `orust.toml`, translate to the generated manifest |
| `fmt` | `--check`, `--all` | same meaning as cargo fmt; cargo's `-- <rustfmt args>` forwarded only with `--rust` |
| `new`, `init` | `--lib`, `--bin`, `--name`, `--edition`, `--vcs` | same meaning as cargo |
Any collision found by the automated flag-diff test that is not in this file fails CI until a decision is logged.

ORust-only global flags (accepted before or after the command, before any standalone `--`):
`--raw` (no translation, no generation: run cargo as given; implies `--no-generate`), `--no-generate` (reuse the existing generated tree), `--show-cargo` (print the exact cargo command and environment changes to stderr, then run it), `--show-original` (print rustc's original diagnostic after ours), `--show-generated` (include diagnostics that have no `.or` origin), `--explain-level beginner|intermediate|expert`. Flags cargo also defines (`-v`, `-q`, `--color`, `--offline`, `--frozen`, `--locked`, `--config`, `-Z`) are NOT consumed by ORust; they are forwarded to cargo and ORust only observes them (for example `--color never` also disables our colors, `-q` suppresses our banners).

## Argument model
- Grammar: `orust [+toolchain] [GLOBAL-ORUST-FLAGS] <command-or-alias> [ARGS...] [-- PROGRAM-ARGS...]`.
- `+toolchain` as the first argument is forwarded to the cargo invocation (works only when cargo is a rustup proxy; otherwise print a clear error).
- Parse only what ORust owns: the command name, ORust-only flags, `.or` positional paths for single-file mode, and for Replaced and Native commands their full flag sets (clap). For Enhanced and Passthrough commands, do NOT model cargo's flags in clap; extract our own flags and forward the rest as an opaque argument vector.
- Anything after the first standalone `--` belongs to the program or test binary and is forwarded verbatim; injected flags (like `--manifest-path` and `--message-format`) are inserted BEFORE that `--`.
- Argument order is preserved. Flags ORust injects go last (before `--`), and are never duplicated if the user already supplied them (if the user passes `--message-format`, honor it and skip translation for that invocation, except that `--message-format=json*` is passed straight through).
- Use `OsString` end to end; never assume UTF-8.
- Environment: honor `CARGO` (or `ORUST_CARGO`) for the cargo binary, `CARGO_HOME`, `CARGO_TARGET_DIR`, `RUSTC`, `RUSTFLAGS`, `RUSTUP_TOOLCHAIN`, `CARGO_TERM_COLOR`, `NO_COLOR`. Set `CARGO_TARGET_DIR` to `<root>/target/cargo` ONLY when unset (log the decision), so generated crates share one target dir and `orust clean` knows what to remove.

## Execution pipeline (for Enhanced commands)
1. **Locate.** Walk up from the cwd (or from `--manifest-path`) for `orust.toml`. Not found: if a `Cargo.toml` is found, run cargo unchanged (plain Rust project; exit code and streams preserved; no banner). If neither exists, run cargo unchanged and let cargo report.
2. **Generate.** Unless `--no-generate`/`--raw`, run the incremental generator (milestone 51). Parse and lowering errors are ORust errors, printed in `.or` form, exit code 1, and cargo is NOT invoked. Never rewrite a generated file whose bytes did not change.
3. **Sync the lockfile.** The root `Cargo.lock` is canonical (commit it). Before invoking cargo copy it into the generated project when bytes differ; after a command that can change it, copy it back only if bytes changed. No symlinks (Windows). Test that two consecutive builds touch neither file's mtime.
4. **Invoke cargo.** Same cwd as the user, `--manifest-path <generated>/Cargo.toml`, forwarded args, injected `--message-format=<json variant>` when ORust is translating (compiler-invoking commands only).
5. **Stream.** Read stdout line by line. Cargo JSON lines of `reason = compiler-message` go through the diagnostics translator (milestones 3-4, 20, 61), everything else (build-finished, artifacts) is consumed or forwarded as appropriate, and non-JSON lines pass through unchanged and in order. Diagnostics appear as they arrive, not at the end. Diagnostics whose primary span has no `.or` origin are hidden by default, counted, and summarized once ("3 warnings in generated code hidden; use --show-generated").
6. **`run`/`test`/`bench`:** two phases. Phase 1 builds with translated diagnostics. If it succeeds, phase 2 executes the produced binary directly (using the `executable` path from the artifact messages) with inherited stdin, stdout, and stderr and the cwd cargo would have used, so program I/O is never mixed with ours. If phase 1 fails, do not run. For `test`, ORust doctests (milestone 42) run as an additional phase unless `--no-doc`.
7. **Signals.** Forward Ctrl-C to the child process group (Unix) or use a job object (Windows); never leave orphan builds. A second Ctrl-C kills immediately.
8. **Exit.** Exit with the child's code. If ORust itself fails before spawning (generation error, cargo not found), exit 1 with a friendly message ("`orust` needs cargo. Install Rust from rustup.rs, or set ORUST_CARGO").

## Help and listing (the visible deliverable)
`orust --help`, `orust help`, `orust` with no arguments, and `orust --list` print one merged view in this order: ORust commands, cargo commands enhanced by ORust, plain cargo commands, aliases, third-party extensions. Each row ends with its origin tag. Columns align at the terminal width (query width; default 80; truncate descriptions with an ellipsis, never wrap mid-column; honor `--color`, `NO_COLOR`, and a `--ascii` mode with no box characters or emoji). Tags are always printed as text so the output stays meaningful without color.

Target shape (wording can be refined; structure and tags are the contract):

ORust: Rust with a friendlier front door.

## Help rules
- **Command source of truth.** The rows come from the routing registry plus discovery (milestone 64), never from a hand-written list. A routing-versus-help consistency test fails CI if a tag disagrees with the real routing.
- **Per-command help** (`orust help build`, `orust build --help`, `orust build -h`): print, in order, (1) a header with the origin tag and one sentence on what ORust changes for this command, (2) an "ORust adds" section listing only ORust-specific flags and behaviors for that command, (3) for `[cargo+]` and `[cargo]` commands, a "From cargo" section containing cargo's own `cargo <cmd> --help` output **captured at runtime from the installed cargo**, unmodified and clearly separated, so users always see the real flags for their cargo version. For `[orust]` commands there is no cargo section. If capturing cargo's help fails, say so and show only the ORust part.
- **Collisions are visible.** Where the collision registry gives ORust a different meaning (for example `test --doc`), the flag is listed in "ORust adds" with a note and the cargo meaning is shown with its `orust cargo ...` spelling.
- **Unknown command.** Exit code 2 with did-you-mean suggestions drawn from every known name (commands, aliases, extensions), for example "no command `biuld`. Did you mean `build`?". If cargo itself would accept the name (an extension appearing after startup, for example), forward rather than reject; only reject when discovery says it does not exist anywhere.
- **`--list`:** one command per line, `name<TAB>origin<TAB>description`, stable order, no color, no banner. `--list --format json` emits `[{name, origin, description, source, expansion?}]` with a documented schema (`docs/cli-json.md`). Output purity is tested.
- **Width and style.** Query terminal width, honor `NO_COLOR`, `--color`, and `--ascii`. Descriptions truncate with an ellipsis. Tags never truncate. In a pipe, output is plain and uncolored.
- **First line shows what is wrapped:** `orust <version> (wraps cargo <v>, rustc <v>)`, using the actual installed versions. If cargo is missing, print `cargo: not found` and a short fix.

## Aliases
- **Sources, highest precedence first:** (1) `[alias]` in the nearest `orust.toml`, (2) `[alias]` in `~/.config/orust/config.toml`, (3) cargo's `[alias]` tables from `.cargo/config.toml` (discovered by walking up, then `$CARGO_HOME`), (4) cargo's own built-in aliases (`b`, `c`, `r`, `t`, `d`, and others; read them from `cargo --list`, do not hard-code). Verify cargo's own precedence and log differences.
- **Syntax in orust.toml:**
````
[alias]
b  = "build"
rr = "run --release"
ck = ["check", "--all-targets"]          # array form keeps argument boundaries exactly
ship = "publish --dry-run"
````
- String aliases split on whitespace only unless cargo's rules (verified earlier) allow quotes; array aliases are exact. Document which, and test quoting edge cases.
- An alias may expand to a Native, Replaced, Enhanced, Passthrough, or Extension command, or to another alias. Detect cycles (`a -> b -> a`) and cap depth at 8 with a clear error naming the chain. An alias may NOT shadow a Native or Replaced command, or any name in the registry: error "`new` is already an orust command; pick another alias name". Aliases may shadow only each other across sources (higher precedence wins, with a `orust alias list` note).
- Expanded arguments are prepended to the user's remaining arguments; ORust flags inside an expansion are honored.
- `orust alias list [--format json]` shows each alias, its expansion, source file, and whether it is shadowed. `orust --show-cargo` prints the final expansion.

## Config (`orust.toml` and user config)
````
[cli]
translate = true            # false: never translate diagnostics (same as --raw for diagnostics only)
banner = true               # versions line on commands that print help
show_cargo = false          # same as always passing --show-cargo
color = "auto"
target_dir = "target/cargo" # default location for the shared CARGO_TARGET_DIR (used only if CARGO_TARGET_DIR is unset)

[cli.extensions]
nextest = { run_in = "generated", translate = true }
deny    = { run_in = "root" }
````
Precedence: flags, then environment (`ORUST_*`), then project `orust.toml`, then user config, then defaults. Unknown keys warn, not fail.

## The `cargo orust` shim
Ship a second binary `cargo-orust` (the same code, detected by argv[0]) so `cargo orust build` works and the cargo ecosystem treats `orust` as a subcommand. It simply drops the leading `orust` argument and continues as `orust`. Verify the exact argv shape cargo passes to external subcommands and the environment it sets (log in decisions). `cargo orust` and `orust` must behave identically; test both entry points over the same fixtures.

## Acceptance scenarios (each is a test)
1. `orust --help` in a directory with no project shows all six sections with correct tags, cargo versions on the first line, and exits 0; the output contains no ANSI codes when piped.
2. `orust build` in an ORust project with a use-after-move error prints the friendly `.or` error, exits 101 (cargo's code for build failure on the verified toolchain), and does not print rustc's original text unless `--show-original`.

## Testing requirements
- All CLI tests use the recording fake `cargo` unless explicitly in the "real cargo" job. The real-cargo job runs on the CI matrix (MSRV, stable, beta) and checks: `cargo --list` parsing, flag-diff collisions, JSON message shapes, and one end-to-end build per acceptance scenario.
- Snapshot tests for help, `--list`, `alias list`, `doctor`, and `which`, each at several widths and in ascii/color/plain modes.
- Property tests: argument passthrough, alias expansion boundary preservation, `OsString` round-trips including invalid UTF-8 on Unix and unpaired surrogates on Windows.
- Output purity tests: nothing from ORust (banners, notes, warnings) appears on stdout in `--message-format=json*`, `--format json`, `metadata`, or `--list` modes; notes go to stderr and are suppressed by `-q`.
- No network and no wall-clock sleeps in default CI; signal tests use a fake cargo that blocks until killed.
- CI order: `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test --workspace`, then the real-cargo job, then completion-script smoke tests.

Notes:

- **The key design decision is the six origin tags.** I chose `[cargo+]` (cargo run on your generated Rust, errors translated) versus `[cargo]` (untouched) so users always know when ORust is involved. A test makes sure the tag always matches the real routing, so help can't mislead.
- **Some cargo commands are deliberately *replaced*, not wrapped.** `cargo fix` or `cargo add` would edit the generated files, which ORust overwrites on the next build. So `orust add` edits `orust.toml` instead, and `orust fix` does ORust migrations.
- **The `test --doc` flag collides.** In cargo it means Rust doctests; in ORust it means ORust doctests. The prompt gives ORust's meaning priority and keeps `orust cargo test --doc` as the way to the original. A flag-diff test against real `cargo --help` output catches any other collisions automatically.
- **Several cargo details need checking on a real install**, because I can't verify them from here: the `cargo --list` format, how aliases are split, and what cargo passes to external subcommands. The prompt makes those the first thing Codex tests and logs.
