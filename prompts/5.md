# Project: rustplain: plain-language explanations for any rustc error

Working name `rustplain` (binary `rustplain`, cargo subcommand `cargo plain`). Check crates.io for name conflicts before publishing; the name can change without affecting the design.

## What we're building
A standalone, offline, deterministic tool written in Rust that sits between `rustc`/`cargo` and the human. It consumes rustc's own structured JSON diagnostics and re-presents each one as a plain-language explanation: what happened, why Rust has this rule, the sequence of events in the user's own code, and ranked fixes (with exact diffs when rustc or our own verified analysis supports them). It works on ANY Rust project. It has no knowledge of, or dependency on, any other language or transpiler.

Audience: people learning Rust, people coming from Java/C#/Dart/Swift/Python/C++, and teachers. The tool never replaces rustc's checks; rustc stays the source of truth.

## Hard rules (save this section as AGENTS.md)
1. **rustc is the source of truth.** Never reimplement the borrow checker, type checker, trait solver, or name resolution. We only translate and explain what rustc already decided.
2. **Structured fields first, message text last.** Match on `code`, span labels, children, and applicability. Use regex on message text only for diagnostics that have no code, or as a last-resort fallback. rustc's wording changes between versions; our matching must degrade gracefully.
3. **Never fabricate.** Show a code diff only if it comes from rustc's own suggestion or from an edit we generated and verified (see milestone 11). Otherwise describe the fix in words. If no rule matches, show a cleaned-up version of rustc's original message. Never invent an explanation to fill space.
4. **Honesty labels.** Every explanation carries a confidence level (High / Medium / Low). Low confidence is shown with "I'm not sure this is the cause; here is rustc's original message".
5. **Always escapable.** `--raw` bypasses everything and prints rustc's original output. `--show-original` prints it after ours. Exit codes always match the underlying cargo/rustc exit code.
6. **Offline and private.** No network access, no telemetry, no code leaves the machine. Link text points to docs but is never fetched at runtime.
7. **Never panic on bad input.** Each rule runs inside `catch_unwind`; a crash or unexpected shape falls back to the original diagnostic. Unknown JSON fields and unknown `level`/`applicability` values are tolerated.
8. **The user's code, not ours.** Snippets show the user's real source (from the JSON `text` fields or the file). Never show macro-internal or std-internal code as if it were the user's; point at the outermost user-written span.
9. **Content lives in data, logic lives in Rust.** Explanation text is in templates under `templates/<lang>/`, so people can contribute wording (and translations) without writing Rust.

## Tech choices and dependency budget
- Rust 2021+, Cargo workspace, MSRV pinned in `rust-toolchain.toml` and tested in CI. Dual license MIT/Apache-2.0.
- **Budget (default build):** `serde` + `serde_json` (parse), `clap` (CLI), `anstream`/`anstyle` (color, NO_COLOR, tty detection), `unicode-width` (columns), `similar` (diffs), `thiserror`. A tiny hand-written `{{var}}` template engine is preferred over `minijinja`; if you need more, log it. Dev-only: `insta`, `proptest`, `assert_cmd`, `tempfile`.
- **Optional features (off by default):** `analysis` (adds `syn` for finding the enclosing fn/type to build verified fixes), `lsp-bridge`, `regex-fallback` is NOT optional: use the `regex` crate only inside the codeless-message matcher module.
- No async runtime, no network crates, no proc-macros of our own.
- Every new dependency needs a one-line justification in `docs/decisions.md`.

## Input formats (the data model)
Cargo with `--message-format=json` emits one JSON object per line. Relevant `reason` values: `compiler-message` (wraps a diagnostic in `message`), `compiler-artifact` (has `executable`, `target`, `package_id`), `build-script-executed`, `build-finished` (has `success`). Raw rustc with `--error-format=json` emits bare diagnostic objects.

Diagnostic object: `message`, `code` (`{code, explanation}` or null), `level` (`error`, `warning`, `note`, `help`, `failure-note`, `error: internal compiler error`), `spans[]`, `children[]` (recursive diagnostics: notes and helps), `rendered`.
Span object: `file_name`, `byte_start`, `byte_end`, `line_start`, `line_end`, `column_start`, `column_end` (1-based, character columns), `is_primary`, `text[]` (`{text, highlight_start, highlight_end}`), `label`, `suggested_replacement`, `suggestion_applicability` (`MachineApplicable`, `MaybeIncorrect`, `HasPlaceholders`, `Unspecified`), `expansion` (macro backtrace, nested).

Requirements:
- Model everything with `#[serde(default)]` and `Option`; test against fixtures from at least stable, beta, and the MSRV toolchain.
- Columns are characters, not bytes: handle multi-byte and wide (CJK/emoji) characters and tabs when drawing underlines.
- Spans in `/rustc/<hash>/library/...`, `~/.cargo/registry/...`, or missing files: never try to render a source snippet; show as a one-line note ("in the standard library: `Iterator::next`").
- Macro expansions: climb `expansion.span` to the outermost user-written span for the primary location, and say "inside the `vec!` macro" when relevant.
- Preserve diagnostic order and group each top-level diagnostic with its children.
- Filter noise (`aborting due to N previous errors`, `could not compile`) from the explanation list, but use the counts in the final summary.

## The explanation model
```rust
struct Explanation {
    headline: String,            // one plain sentence, uses the user's names
    what_happened: String,       // 1-3 sentences, no jargon, or jargon defined inline
    story: Vec<Event>,           // ordered events in the user's code (see below)
    why_rust_cares: String,      // the underlying rule, in one short paragraph
    fixes: Vec<Fix>,             // ranked, each with title, why, tradeoff, optional Edit
    learn_more: Vec<Link>,       // error index + Rust Book chapter (static URLs)
    confidence: Confidence,
    codes: Vec<String>,          // rustc code(s) translated
    original: Diagnostic,        // always retained
}
struct Event { kind: Created|Moved|Borrowed|BorrowedMut|Used|Dropped|Returned|Captured|Assigned|Required, span: Span, note: String }
struct Fix { title: String, why: String, tradeoff: String, edit: Option<Edit>, applicability: Applicability, verified: bool }
```
`story` is the heart of the tool: for ownership and borrowing errors, build a timeline from rustc's labeled spans ("value moved here", "first mutable borrow occurs here", "borrow later used here") and re-label each event in plain words using the user's identifiers.

## Rule engine
```rust
trait Rule {
    fn id(&self) -> &'static str;                      // e.g. "borrowck.move.use-after-move"
    fn matches(&self, d: &Diagnostic, cx: &Cx) -> Option<Matched>;
    fn explain(&self, d: &Diagnostic, m: Matched, cx: &Cx) -> Explanation;
}
```
- Registry dispatches first by `code`, then by ordered message-pattern rules for codeless diagnostics, then to the generic fallback.
- Each code has **variants** distinguished by structured evidence, for example E0382: moved into function argument / moved by a method taking `self` (look for the child note "`x` moved due to this method call") / moved into a closure / moved in a previous loop iteration / partial move / moved in a `for` loop (`into_iter`). Each variant has its own template and its own fixtures.
- Generic fallback ("unexplained rule"): show rustc's original message, plus the `code.explanation` text from the JSON if present, plus the error index link. Count these in the coverage metric (milestone 12).
- Templates: `templates/en/<rule-id>.md` with front matter (headline, confidence) and sections (`what`, `why`, `fix.N`). Variables come from `Matched` (names, types, spans). Missing variable renders as the original text, never as an empty hole.
- Levels: `--level beginner|intermediate|expert` (default intermediate). Beginner adds an analogy and defines terms; expert shows only the story, the rule, and the fixes in terse form. Same data, different template sections.

## Example that must work (acceptance for milestones 3-5)
Source:
```rust
fn main() {
    let names = vec![String::from("ada")];
    let moved = names;
    println!("{}", names.len());
}
```
rustc reports E0382 "borrow of moved value: `names`" with labels on the declaration (type does not implement `Copy`), the move (`value moved here`), and the later use (`value borrowed here after move`), plus a help suggesting `names.clone()`.

Expected output (shape, wording can be refined in templates):
```
error[E0382]: you used `names` after giving it away
  --> src/main.rs:4:20
   |
 2 |     let names = vec![String::from("ada")];
   |         ----- `names` owns this Vec<String>
 3 |     let moved = names;
   |                 ----- ownership moves to `moved` here
 4 |     println!("{}", names.len());
   |                    ^^^^^ `names` was already handed away, so it can't be used

What happened: In Rust, every value has exactly one owner. `let moved = names;`
transfers ownership of the Vec to `moved`, because Vec<String> is not `Copy`.
After that, `names` no longer has anything in it.

Why Rust does this: one owner means Rust always knows exactly when to free the
memory, with no garbage collector and no double-free bugs.

Fixes (best first):
  1. Borrow instead of moving:      let moved = &names;
     Both names can read the same Vec. `moved` can't change or outlive `names`.
  2. Make a separate copy:          let moved = names.clone();
     Safe and simple; costs an allocation and a copy of the data.
  3. Stop using `names` afterwards, if `moved` is the real owner now.

Learn more: https://doc.rust-lang.org/error_codes/E0382.html
            https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html
Confidence: high
```
Fix 1 has no rustc suggestion, so it must either be built from a verified edit (milestone 11) or shown as words-only without a diff before then. Fix 2 comes straight from rustc's suggestion and may show a diff immediately.

## CLI
```
cargo plain check | build | test | run | clippy [-- cargo args]    # wrap cargo, explain errors
rustplain --from-json <file|->                                    # read cargo or rustc JSON from a file or stdin
rustplain explain <CODE|lint-name> [--level ...]                  # offline lesson with a failing and a fixed example
rustplain explain --list                                          # all codes we cover
rustplain doctor                                                  # toolchain version, JSON health check, coverage for this rustc
rustplain coverage                                                # dev: coverage report over the mutation corpus
```
Global flags: `--level`, `--format terminal|plain|markdown|json|github|cargo-json`, `--color auto|always|never`, `--ascii` (no box-drawing or emoji), `--show-original`, `--raw`, `--warnings hide|brief|full` (default brief), `--lang en`, `--no-summary`, `--verify-fixes` (milestone 11), `--config <path>`.
Config: `rustplain.toml` in the project root or `~/.config/rustplain/config.toml`; CLI flags win.
- Exit code: identical to the wrapped cargo command. `--from-json` exits 1 if any error-level diagnostic is present, else 0.
- `NO_COLOR` is respected; piped output defaults to `plain`.
- Alias example in docs: `[alias] p = "plain check"` in `.cargo/config.toml`.

## Milestones (do in order; commit after each; keep tests green)

**P1: Skeleton and data model.** Workspace, `rustplain-diag` with tolerant types, JSON-lines reader that streams, `--from-json` mode, fallback renderer that prints a cleaned-up original (headline, snippet from `text` fields, children as notes). Fixture harness: `fixtures/<code>/<variant>/{src.rs, rustc.json, expected.*}`; `cargo xtask capture <path>` runs `rustc --error-format=json --edition 2021 --crate-type lib` (or cargo for project fixtures) with the current toolchain and records `rustc --version -v` beside the JSON. Round-trip test: parse then re-serialize loses nothing important.

**P2: Cargo wrapper and streaming.** `cargo plain check|build|clippy` spawns cargo with `--message-format=json`, processes lines as they arrive (diagnostics appear in real time), passes through anything that isn't a diagnostic, and preserves the exit code. For `run` and `test`: phase 1 builds with JSON diagnostics; on success, execute the binary or test executables using the `executable` path from `compiler-artifact` messages so the program's own stdout/stderr stay clean and in order; on failure, do not run. Empirically verify (and log in `docs/decisions.md`) how cargo's cached-warning replay behaves so users never see the same diagnostic twice. Handle workspaces (`package_id`, relative path normalization), `--package`, `--workspace`, `--release`, and arbitrary trailing cargo args.

**P3: Renderer.** Snippet drawing with multi-line spans, multiple labels per line, overlapping underlines, tab/wide-char handling, line-number gutter, and `--ascii` mode. Events in the story get distinct markers (`-`, `^`, `~`) and short plain labels. Formats: `terminal` (ANSI), `plain`, `markdown` (for pasting into chats and issues), `json` (our `Explanation` objects, schema documented in `docs/json-schema.md`), `github` (workflow annotation commands). Snapshot-test every format with `insta`.

**P4: Rule engine, templates, explain command.** Registry, matching order, template loader with the tiny `{{var}}` engine, `catch_unwind` safety net, confidence labels, levels, summary footer. `rustplain explain <code>` prints: the rule in plain words, a minimal failing example, a fixed example, and links. **Test requirement:** every registered `explain` example is compiled; the failing example must produce exactly that code on the CI toolchain, and the fixed example must compile cleanly. Implement the E0382 acceptance example end-to-end.

**P5: Ownership family.** E0382 (all variants above), E0505 (move out while borrowed), E0507 (move out of a borrow, with the "borrowed content" cases: `&Vec<T>` index, `self.field`, `Option` in a reference), E0381 (possibly uninitialized), E0384 (assign twice to immutable), E0594 and E0596 (cannot assign/borrow as mutable: distinguish "variable not declared `mut`" from "behind a `&` reference" and suggest changing `&T` to `&mut T` in the signature when rustc points at it), E0373 (closure may outlive; `move` fix), E0716 (temporary dropped while borrowed).

**P6: Borrowing and lifetimes family.** E0499, E0502, E0506, E0515 (return reference to local), E0597 (does not live long enough), E0106 (missing lifetime specifier; explain elision rules and the "which input does the output borrow from?" question), E0261 (undeclared lifetime), E0521 (borrowed data escapes), E0310 (type may not live long enough), and the codeless **"lifetime may not live long enough"** family (match on message text plus child notes; this has no error code). Each explanation draws a lifetime timeline: where each borrow starts and its last use, in the story.

**P7: Types and traits family.** E0308 (mismatched types: `&String` vs `&str`, `i32` vs `i64`, `Option<T>` vs `T`, missing `Ok(...)`, unit vs value because of a trailing semicolon: detect rustc's "remove this semicolon" help), E0277 with variants (`?` conversion failure, `?` in a function returning `()`, trait bound not satisfied, `Send`/`Sync` for threads and `spawn`, `Sized`, `Display`/`Debug` missing, cannot index, cannot compare, `Iterator` not implemented), E0599 (method not found: distinguish missing trait import, wrong type, private, and Option/Result needing `.unwrap()`-style handling), E0282/E0283 (type annotations needed), E0369 (binary op), E0038 (not dyn-compatible), E0046/E0053/E0050 (trait impl mismatches), E0117/E0119 (orphan and overlapping impls), E0061 (wrong argument count), E0063 and E0560 (struct fields), E0614/E0618.

**P8: Names, modules, patterns, syntax.** E0425, E0412, E0423, E0424, E0428, E0432, E0433, E0434, E0435, E0603, E0616, E0624 (privacy: say which module owns it and how to expose it), E0004/E0005 (non-exhaustive and refutable patterns: list missing variants from rustc's note), E0023/E0026/E0027, E0658 (unstable feature), E0133 (needs `unsafe`), and **codeless syntax errors** by message pattern: "expected one of ... found ...", missing/unclosed/mismatched delimiters (point at both the opener and where rustc gave up), missing semicolon, `else` without `if`, unknown macro. For "cannot find X": suggest `use` lines only when rustc itself suggested them.

**P9: Warnings and clippy.** Lints are explained too, but briefly and with severity-aware framing (warnings never block). Cover: `unused_variables`, `unused_mut`, `unused_imports`, `dead_code`, `unused_must_use` (the Result-ignored case teaches error handling), `non_snake_case`/`non_camel_case_types`, `irrefutable_let_patterns`, `unreachable_code`, `deprecated`, and the top ~30 clippy lints by popularity (`needless_return`, `redundant_clone`, `clone_on_copy`, `len_zero`, `collapsible_if`, `manual_map`, `needless_borrow`, `single_match`, `too_many_arguments`, `new_without_default`, etc.). `--warnings brief` shows one line per warning grouped by lint with a count; `full` explains each. Clippy lints get a "why this is considered unidiomatic" paragraph; mark when the suggestion is `MachineApplicable`.

**P10: Multi-diagnostic intelligence.** Real compiles produce many errors, and later ones are often cascades. Implement: (a) dedupe identical spans/messages; (b) cascade detection (errors that mention a type or name that an earlier error already failed to resolve: mark as "probably caused by error #1"); (c) group related ownership errors on the same variable; (d) a recommended order ("Fix #1 first, then re-run; the next 3 errors will likely disappear"); (e) a final summary with counts by category and a "what to learn next" link list. Never hide errors by default; cascades are collapsed with a count, expandable with `--all`.

**P11: Verified fixes (the differentiator).** Goal: show only fixes that are proven to work.
- Collect candidate edits: rustc suggestions (with applicability), plus our own mechanical edits (add `mut`, add `&`/`&mut`, add `.clone()`, add `move`, change a parameter from `T` to `&T`, add `.to_string()`/`.as_str()`, add missing `use` that rustc suggested, remove a trailing semicolon). Use the optional `analysis` feature (`syn`) only for edits that need to find the enclosing function or type.
- `--verify-fixes`: copy the project to a temp dir (respect `.gitignore`, symlink or share `CARGO_TARGET_DIR` to keep it fast), apply one candidate, run `cargo check --message-format=json`, and mark the fix `verified` only if the original diagnostic disappears and **no new error-level diagnostic appears**. Show `[verified: compiles]` or `[unverified]`; drop fixes that introduce new errors, or show them with the new error named ("this fixes E0382 but causes E0502 at line 9").
- `--apply <n>` applies a fix for real, **only** if verified or `MachineApplicable`, prints the diff, and asks for confirmation unless `--yes`. Never edit files without an explicit flag. Never touch files outside the project root.
- Time-box verification (default 10s per candidate, configurable) and run candidates in parallel up to a small limit.

**P12: Quality, coverage, packaging.**
- **Mutation corpus:** a set of small, license-clean, compiling programs (write them ourselves; cover structs, traits, generics, closures, iterators, threads, async, error handling, modules). `cargo xtask mutate` applies mechanical breakages (delete `&`, remove `mut`, remove `.clone()`, rename a variable, delete a `use`, change a type, remove a match arm, swap argument order, delete a `;`, delete a `move`) and records rustc's diagnostics. `rustplain coverage` reports: percent of diagnostics explained by a specific rule vs generic fallback, per code and per variant, plus a list of the most frequent unexplained diagnostics (this is the work queue for new rules). CI fails if coverage regresses.
- **Toolchain matrix:** CI runs the full fixture suite on MSRV, stable, and beta; nightly is allowed to fail but reports drift. A scheduled job re-captures fixtures on the latest stable and opens a diff summary. `rustplain doctor` warns when the installed rustc is newer than the newest toolchain we tested.
- **Never-panic fuzzing:** `proptest`/`cargo-fuzz` target that feeds arbitrary JSON and truncated/corrupted diagnostics through the parser and every rule; assert no panic and a fallback explanation.
- Link check: a test (opt-in, needs network, not run in default CI) verifies every URL in templates; a default test verifies URL shape and that the code in the Error Index link matches the rule.
- `xtask new-rule <CODE> <variant>` scaffolds the rule file, template, fixture directories, and an `explain` example.
- Docs: README with a screenshot-style transcript, `docs/architecture.md`, `docs/writing-a-rule.md`, `docs/templates.md`, `docs/json-schema.md`, `CONTRIBUTING.md` (adding a rule = one template + one fixture + one test), `docs/decisions.md`. Packaging: `cargo install` works, `cargo-binstall` metadata, a GitHub Action example, release binaries for Linux/macOS/Windows.

**P13 (stretch): Editors and CI.**
- `--format cargo-json`: emit diagnostics in the same JSON shape cargo produces, but with `message` and `rendered` rewritten to our headline and explanation, spans and codes untouched. This lets rust-analyzer show friendly messages by setting its check override command to our wrapper (verify the exact setting name and expected output against the current rust-analyzer docs, and document it).
- A VS Code extension stub in `editors/vscode` that shows the full explanation in a panel when the user clicks a diagnostic.
- GitHub Action that posts explanations as PR annotations (`--format github`).
- WASM build of `rustplain-explain` for a web playground that takes pasted JSON diagnostics.

## Testing requirements
- Every code and variant listed above has at least one fixture (source, captured JSON, expected output for `plain` and `json`), and one `explain` example that is compiled in tests.
- Snapshot tests per format and per level for the acceptance example and three more per family.
- Robustness tests: truncated JSON lines, unknown fields, missing `spans`, spans on missing files, macro-expanded errors, multi-byte and tab-indented source, Windows line endings, very long lines (truncate with an ellipsis and keep the highlighted region visible), and 500+ diagnostics (performance budget: under 1s to process 500 diagnostics, excluding compile time).
- CLI tests with `assert_cmd`: exit codes preserved, `--raw` is byte-identical to cargo's rendered output, `--from-json -` works from a pipe, `run`/`test` do not interleave program output with diagnostics.
- Determinism: the same input JSON always yields byte-identical output.
- CI order: `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test --workspace`, fuzz smoke (60s), `rustplain coverage` threshold check.

## Working rules
- Do not stop to ask questions. When something is ambiguous, pick the simplest option that fits the hard rules and record it in `docs/decisions.md` with a one-line rationale.
- Finish each milestone's tests before starting the next; commit after each milestone.
- Write wording as a patient teacher: use the user's own identifiers, avoid unexplained jargon at the default level, never blame the user.
- When rustc output has no matching rule, add a fixture for it and register a TODO rule id rather than guessing.
